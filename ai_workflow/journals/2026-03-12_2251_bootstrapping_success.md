# Journal Entry: 2026-03-12 22:51 - Completion of Repository Bootstrapping

## Objective
Execute Phase 2 of the workflow: carving the extracted assets using standard repository tools (`splat`), establishing a baseline build, and verifying the compilation via head-to-head byte comparisons against the original disc.

## Actions Taken
1.  **Ran `make setup` in Docker**: Successfully executed `splat` against `config/slus_006.64.yaml` and `config/field.yaml`. This parsed `SLUS_006.64` and `FIELD.BIN` and cleanly carved approximately 250 KB of code into the `src/` and `asm/` directories.
2.  **Ran `make build` in Docker**: Initiated compilation using the provided `gcc` versions and PsyQ translation tools.
    - *Blocker Encountered*: Build failed immediately because `tools/maspsx/maspsx.py` was missing.
    - *Resolution*: Identified `tools/maspsx` as a git submodule. Ran `git submodule update --init --recursive` to pull the assembler translator. Build subsequently completed perfectly.
3.  **Ran `make check` & `make report`**: Validated the compiled byte arrays.
    - *Blocker Encountered*: `sha256sum` failed with a "no file was verified" error.
    - *Resolution*: Discovered two issues. First, `config/checksum.sha` used Windows CRLF line endings, breaking the Linux verification tool. Installed and ran `dos2unix` inside the container. Second, the checksum file incorrectly referenced `FIELD.bin` instead of the `FIELD.BIN` generated by the build process. Capitalization was corrected.
    - *Outcome*: Output passed checksum validation and `objdiff` successfully generated the first `progress.json` matrix.

## Meta-Learnings & DKB Updates
- The pipeline relies heavily on git submodules being fully initialized.
- Linux CLI tooling (`sha256sum`) is highly sensitive to line-endings (`\r\n` vs `\n`).
- Both of these observations have been documented centrally in `ai_workflow/knowledge_base.json` under `build_gotcha_001`.
